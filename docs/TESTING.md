# Quality Assurance — Test Plan & Documentation

**Product:** Online Course (Next.js dashboard + external REST API)  
**Purpose:** This document describes what is tested, how tests are run, and how they relate to formal test cases. It is the single reference for engineering and QA.

---

## 1. Scope

| Layer | What is covered | What is *not* covered here |
|--------|------------------|-----------------------------|
| **API (service clients)** | HTTP calls from `services/*.ts` to `{NEXT_PUBLIC_API_URL}` — URLs, methods, headers, bodies, success payloads, and common error shapes | Live integration against a running backend (no real `9091` required for CI) |
| **Frontend (logic & UI units)** | Zod form rules (`types/auth.ts`), course card mapping (`lib/category-utils.ts`), presentational components (`Logo`) | Full browser E2E (login flow, dashboard pages, NextAuth in a real browser) |
| **Manual / E2E** | Documented in the Excel matrix as not yet automated | Middleware redirects, NextAuth, `/dashboard/groups` with real data |

Automated tests use **mocked `fetch`** so results are repeatable in CI and offline.

## 2. Test artifacts (formal traceability)

| Artifact | Location | Role |
|----------|-----------|------|
| **Test case matrix (Excel)** | `docs/test-cases-matrix.xlsx` | Human-readable cases: ID, area, feature, description, type, preconditions, **Input data** (sample JSON/credentials; default test password `admin123`), steps, expected result, automation flag, suite |
| **Mock data summary** | Same workbook, sheet **Mock data** | Bulk dataset sizes used in automation (e.g. groups/courses stress counts) |
| **Execution log** | Same workbook, sheet **Run report** | Run summary rows (Vitest totals, environment, link to `vitest-report.json`) + blank per-TC log rows to fill after each campaign |
| **Machine-readable run report** | `docs/vitest-report.json` | Generated by `npm run test:report` — pass/fail counts and per-test status (suitable for tooling) |
| **DB bulk seed (reference)** | `db/seed.sql` | PostgreSQL DDL + large synthetic dataset aligned with API-style fields; adapt table names to your backend before running |
| **This document** | `docs/TESTING.md` | Strategy, scope, traceability to code, execution instructions |

Regenerate the spreadsheet after changing the matrix script:

```bash
npm run generate:test-excel
```

## 3. Automated test inventory (code ↔ feature)

### 3.1 API client tests (`tests/api/`)

| Test file | Service / API area | Typical endpoints (backend) |
|-----------|-------------------|------------------------------|
| `auth.service.test.ts` | Authentication | `POST /api/v1/auth/login`, `GET/PUT .../profile`, forgot-password, verify-otp, reset-password |

| Path | Role |

## 4. Environment & configuration

- **Base URL in tests:** `vitest.config.ts` sets `NEXT_PUBLIC_API_URL` to `http://localhost:9091` for consistent URL expectations. Mocked responses mean the port does not need to be listening during `npm test`.
- **Production / staging:** Point `NEXT_PUBLIC_API_URL` at the target API when running the **application**; automated tests remain mocked unless you add separate integration jobs.

---

## 5. How to execute

```bash
cd Online-course
npm install          # first time
npm test             # default: Vitest run, all suites
npm run test:watch   # interactive during development
npm run test:coverage # coverage summary (v8)
npm run test:report   # verbose + writes docs/vitest-report.json
```

**Pass criteria:** All automated tests pass; `vitest-report.json` shows `"success": true` and `numFailedTests: 0`.

---

## 6. Reporting (how we document a run “for real work”)

1. Run `npm run test:report`.
2. Keep or archive `docs/vitest-report.json` with the build/release (or attach in CI).
3. For human sign-off, use **`docs/test-cases-matrix.xlsx`**: mark manual rows executed, note date/build, and attach screenshots for E2E if required by your process.

## 7. Gaps & next steps (optional hardening)

- **Playwright (or similar)** for true E2E: login, dashboard, groups page against `next dev` + live API.
- **Contract tests** against OpenAPI/Swagger if the backend publishes a spec.
- **CI job** that runs `npm test` on every push (GitHub Actions, etc.).
